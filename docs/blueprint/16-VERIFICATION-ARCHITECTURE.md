# RustOSRS Verification Architecture

Status: **Normative verification blueprint, corrected by M10 foundation audit**  
Decision class: `PROJECT_DECISION`

Governing rule:

> Test the earliest layer that owns a behavior, and use the strongest independent comparison that layer permits.

A higher-level screenshot never excuses a wrong decoder, transform, plane, normal merge, terrain builder, priority order, or integer contour result.

## 1. Verification levels

### V0 Decode

Owns exact cache/decode behavior: opcodes/defaults, full-width IDs, floor/model/map/loc/texture/sequence/var inputs, revision gates, malformed-input handling.

Preferred comparison: exact decoded values.

### V1 Semantic

Owns model/scene meaning: placement, footprints, morphs, contouring, animation state, model transforms, normals/lighting, terrain construction, bridges/min-plane state, exact software priority oracle inputs.

Preferred comparison: exact values, arrays, topology, identities, and ordering.

### V2 Render structural

Owns extraction without physical-GPU dependence: coordinate rebase, immutable snapshots, face admission/suppression, material mapping, static/dynamic/ordered classification, priority/alpha preparation, zones, picking tables, deterministic draw descriptions.

Preferred comparison: exact extracted artifacts and deterministic command/packet descriptions.

### V3 Reference visual differential

Owns claims that RustOSRS visually matches a named external target renderer.

Examples:

- fixed-camera terrain/model frame;
- reverse-Z/culling/bias;
- alpha composition;
- texture sampling;
- bridge/roof visibility;
- composed scene appearance.

**V3 requires an external oracle artifact.** A screenshot generated by RustOSRS itself can detect regressions, but it cannot by itself prove parity with OSRS or RuneLite.

### V3R Internal reference regression

RustOSRS-generated deterministic Reference images are retained as a separate regression layer:

- fixed camera/profile/tick;
- stable backend/adapter metadata where relevant;
- exact image hash or explicit tolerance.

Passing V3R means "RustOSRS still renders like its accepted Reference baseline." It does **not** mean "1:1 with external OSRS/RuneLite."

### V4 Enhanced presentation

Owns intentional non-reference presentation such as MSAA, enhanced filtering, fog, overlays, optional lighting, and editor diagnostics.

### V5 Editor/document behavior

Owns commands, transactions, undo/redo, persistence, recovery, stale-generation handling, export validation, and editor selection behavior.

## 2. Evidence ladder

```text
pinned source / captured external oracle
              |
              v
        exact fixture
              |
              v
      Rust exact test
              |
              v
   semantic golden scene
              |
              v
 render-structural assertion
              |
              +-------------------+
              |                   |
              v                   v
  internal image regression   external visual differential
          V3R                       V3
```

No branch on the right can replace an earlier exact semantic proof.

## 3. Source oracle policy

Permitted source/oracle classes:

- pinned public melxin/deob source;
- exact checked-in source-derived tables/fixtures;
- imported RuneLite source, identified by exact RustOSRS tree/blob and classified as renderer/API evidence;
- historical local harness only where exact checked-in bytes are pinned and public source corroborates the behavior;
- independent FileStore/rs-cache implementations as corroboration unless explicitly promoted;
- externally captured reference images only when capture provenance is recorded.

Production crates never depend on `osrs-reference` or external Java tooling.

## 4. Fixture identity

Every promoted fixture records:

```text
fixture id/schema
owned spec ids
parity level
oracle kind/repository
commit/tree/blob pins
source paths/symbols
harness revision where applicable
normalized input description
expected output/hash
normalization rules
cache/profile identity where applicable
```

A fixture without reproducible provenance remains research evidence.

## 5. Exact comparison policy

Use exact equality for exact domains, including:

- IDs/opcodes/defaults;
- integer coordinates/vertices;
- triangle topology;
- planes/footprints/orientations;
- HSL helpers and terrain builder intermediates where integer-defined;
- normals and merged normals;
- face render type/priority/raw alpha/texture/bias;
- transform and contour output;
- bridge/min-plane/original-plane state;
- software priority emission order;
- renderer structural packet membership;
- zone keys/generations;
- semantic hashes.

Do not introduce epsilon merely because data will eventually reach a GPU.

## 6. Floating/raster tolerance

Tolerance is allowed only for contracts that are inherently floating/raster/adapter-sensitive.

Every tolerant test documents:

- why exact comparison is inappropriate;
- metric/threshold;
- allowed changed-pixel fraction or mask if any;
- backend/adapter/driver assumptions;
- whether the test gates all CI or only a canonical GPU runner.

## 7. High-risk differential pattern

```text
same normalized input
      |                  |
      v                  v
pinned oracle       Rust implementation
      |                  |
      +------ exact ------+
              compare
```

Ordinary CI consumes checked-in expected artifacts. Regeneration is a separate explicit developer action.

## 8. Required semantic fixture families

### Model/placement

- loc types/orientations and wall-decoration offsets;
- footprints and exact center heights;
- typed/untyped model selection;
- mirroring/winding;
- combined transform order;
- shared-source immutability.

### Normals/lighting

- flat/smooth base normals;
- cross-model positive/no-match/translated cases;
- hide true/false;
- dual-arm wall merge;
- wall/game/floor neighbor merge;
- same-plane versus plane-above hide behavior;
- merged-normal lighting delta;
- decoded contrast `*25` boundary;
- raw alpha `-1/-2` lighting sentinels;
- suppressed `c == -2` face downstream exclusion.

### Morph/animation/contour

- varbit/varp/fallback/null morph;
- footprint-changing morph;
- deterministic legacy pose/progression/replacement;
- contour flat/slope/threshold/border cases;
- source immutability.

### Terrain

- all 13x4 shape/rotation outputs;
- flat diagonal and sentinel skip;
- weighted-HSL definitions;
- source-pinned `class470.method9712` builder differential covering:
  - slope lighting;
  - placement-derived shadow grid;
  - separable 11x11 underlay blend;
  - overlay texture/magenta/secondary branches;
  - jitter-independent 3D corner colors;
  - jittered palette/minimap output if represented;
  - `minPlane` output;
  - normal-finalization/link-below ordering.

### Planes/bridges

- source/collision/storage planes;
- four-plane link-below;
- mutable `plane` versus `originalPlane`;
- `minPlane` ordinary/bit8/bridge cases;
- renderer maplevel/roof grouping without semantic mutation.

### Face/material

- priority 0..11 software oracle;
- imported RuneLite render-mode classification as a separate fixture family;
- alpha sentinel and ordinary values;
- strict reverse-Z equal-depth behavior;
- bias at multiple distances;
- UV reconstruction;
- texture zero-pixel transparency/cutout;
- Reference sampler wrap/min/mag behavior;
- deterministic texture animation.

## 9. Golden semantic scenes

A golden scene contains deterministic semantic state, not merely a screenshot:

- target profile/cache identity;
- input regions or synthetic definition;
- object placements;
- varbit/varp state;
- animation/tick state;
- expected semantic summary/hash;
- expected extraction summary where applicable.

The same scene should drive V1, V2, V3R, and where an external capture exists, V3.

## 10. External visual oracle policy

Before RustOSRS claims external visual parity for a behavior, record a reference artifact produced independently of the RustOSRS renderer.

Acceptable examples:

- deterministic RuneLite frame/capture from an exactly identified imported/upstream renderer configuration;
- deterministic client/deob render harness output with exact source/camera/scene identity;
- another independently implemented renderer only when explicitly classified as corroborating rather than authoritative.

Each external visual manifest records:

```text
oracle renderer/version/source identity
scene/cache identity
camera/projection
viewport
tick/animation state
plane/roof state
texture/filter configuration
depth/render mode configuration
capture method
image hash
comparison metric/tolerance
```

Until such an artifact exists, documentation may claim exact semantic/render-structural parity and internal visual regression stability, but not measured "1:1" external visual parity.

## 11. Internal screenshot policy

RustOSRS Reference images record viewport, camera, tick, visibility state, profile version, backend/adapter metadata, expected hash, and tolerance if required.

These images are V3R regression fixtures. They are still valuable, but their evidence class must be named correctly.

## 12. Generation/concurrency verification

Any asynchronous derivative requires stale-result tests:

- scene generation N finishing after N+1;
- changed zone ticket N rejected after newer invalidation;
- unchanged zone allowed to remain reusable across unrelated generation advancement;
- stale pick cannot alter current selection;
- stale validation/autosave cannot overwrite newer state.

Use deterministic barriers/channels rather than sleep timing.

## 13. GPU lifecycle verification

Future GPU tests cover:

- resource rebuild after simulated loss;
- semantic scene unchanged across renderer recreation;
- zone resources rebuilt only from accepted generations;
- capability failure surfaced explicitly;
- Reference depth/sampler/profile state restored exactly.

Logic-level renderer tests remain mandatory where CI lacks a physical GPU.

## 14. Property/fuzz verification

Property tests target index validity, transform invariants, zone invalidation coverage, semantic hash stability, and command apply/revert identity.

Fuzz targets cover cache/model/object/floor/map/loc/project/export parsers. Robustness tests do not replace reference parity fixtures.

## 15. Merge-gate philosophy

A launchable editor or plausible screenshot is never sufficient by itself.

Minimum milestone evidence:

- decoder: V0;
- semantic construction: V0+V1;
- renderer extraction/M10: V0+V1+V2;
- first GPU renderer: lower tiers plus raster logic and V3R;
- external visual parity claims: V0+V1+V2+V3;
- enhanced presentation: lower parity tiers plus V4;
- editor mutation/persistence: V5 suites.

The current foundation audit explicitly leaves full `TERRAIN-004` implementation and external V3 capture as open gates rather than hiding them behind self-generated visuals.
