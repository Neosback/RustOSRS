## SPEC: TERRAIN-001

**Domain:** `OSRS_SEMANTIC`  
**Status:** `VERIFIED`  
**Executable evidence:** existing shape/rotation golden fixture

### Applies to

Shaped tile topology generated by `SceneTileModel`.

### Required behavior

The semantic terrain model supports exactly the audited shape templates `0..12` for this target snapshot. Shape plus rotation determines:

- template vertices;
- integer local positions;
- interpolated height;
- interpolated underlay/overlay color inputs;
- face count and indices;
- underlay/overlay ownership per face;
- optional face texture assignment.

Rotation remapping follows the pinned client tables exactly. Generated integer vertices/faces are semantic truth; the renderer may repack them but may not substitute different topology.

One tile is exactly `128` local units. Midpoints, quarter points, height interpolation, and color interpolation preserve Java integer operation order.

### Required tests

Retain exact output for all `13 x 4` shape/rotation combinations and require exact vertex arrays, face indices, color-source selection, texture IDs, and flatness.

## SPEC: TERRAIN-002

**Domain:** `OSRS_SEMANTIC` for terrain surface meaning; imported RuneLite upload is independent structural corroboration  
**Status:** `VERIFIED`

A terrain tile is represented by either a flat paint surface or a shaped model surface according to constructed scene state.

For a flat paint surface, the reference two-triangle split is:

```text
NE, NW, SE
SW, SE, NW
```

The `12345678` sentinel marks a skipped/unrendered surface in the audited reference path.

For shaped terrain, consume the exact topology from `TERRAIN-001`. GPU code does not regenerate terrain templates.

## SPEC: TERRAIN-003

**Domain:** `OSRS_SEMANTIC`  
**Status:** `VERIFIED`

### Underlay definition contract

- opcode `1` supplies underlay RGB;
- post-decode derives HSL state;
- saturation/lightness clamp to `0..255`;
- `hueMultiplier` clamps to at least `1`;
- stored hue is weighted by the multiplier.

The weighted-hue representation remains separate because the terrain builder accumulates weighted hue and hue multiplier independently.

### Overlay definition contract

Defaults:

```text
primaryRgb   = 0
texture      = -1
hideUnderlay = true
secondaryRgb = -1
```

Relevant opcodes:

```text
1 -> primary RGB
2 -> texture id
5 -> hideUnderlay = false
7 -> secondary RGB
```

Post-decode computes secondary HSL when present, then restores/computes primary HSL.

## SPEC: TERRAIN-004

**Domain:** `OSRS_SEMANTIC`  
**Status:** `SOURCE_VERIFIED / CORE PORT EXISTING; LOC-SHADOW WRITER REQUIRED`  
**Primary evidence:** pinned `class470.method9712(WorldView)` and `FriendSystem.addObjects(...)`

### Implementation state (2026-10-10)

`osrs-scene::terrain_load` and `osrs-scene::terrain_build` port the terrain loader (explicit and
noise default heights, plane stacking, empty-region fill) and the complete `method9712` builder
(slope light, shadow subtraction, radius-5 blend, overlay branches, tile emission, minimum plane,
bridge link-below). `crates/osrs-reference/tests/terrain_oracle_diff.rs` compares them line by
line against the real pinned client on real build-241 Lumbridge terrain (11,247 tiles, 935 shaped,
40 linked-below) using `reference-fixtures/terrain/lumbridge-3x3.oracle-*`.

Still required before this row is `EXISTING`: the `FriendSystem.addObjects` shadow-grid writer (it
needs object definitions with `clipped` and placed model heights) and an oracle fixture that
exercises non-empty shadow input. The shadow-grid loop for clipped game objects is inclusive
(`0..=size` on both axes), covers a `(size + 1)` square of corner cells, and runs only when
placement succeeded.

### Correction to the earlier provenance audit

The prior M5/M9 conclusion that the terrain builder was absent from the pinned public source was incorrect. `class470` is largely a text-layout class, but its final static method, `method9712(WorldView)`, is the complete target terrain-construction routine. The source blocker is therefore closed.

This does **not** mean RustOSRS already implements full terrain-color parity. Production implementation and an executable differential fixture remain required before this row may become `EXISTING`.

### Verified construction order and inputs

The pinned builder performs, in order relevant to terrain color:

1. a bounded random walk of global hue and lightness presentation offsets;
2. per-plane slope-light calculation from neighboring height samples;
3. subtraction of a placement-derived shadow grid;
4. separable radius-5 neighborhood accumulation, producing the effective 11x11 underlay blend window;
5. weighted-hue/saturation/lightness averaging for underlay color;
6. per-tile underlay and overlay construction;
7. overlay texture/primary-magenta/secondary-color handling;
8. `Scene.addTile(...)` emission;
9. per-tile minimum-plane assignment;
10. scene normal reconciliation/finalization;
11. bridge `setLinkBelow(...)` relinking.

### Slope lighting

The builder derives X/Z height gradients from adjacent height samples, normalizes the synthetic terrain normal with the client integer/floating conversion sequence, applies the fixed light direction, and subtracts the local shadow contribution before using the result as each corner's lightness adjustment.

Exact arithmetic and operation order are normative for the future production port.

### Placement-derived shadow grid

`Tiles.Tiles_underlays2` is **not** generic adjacent-ground contrast.

`FriendSystem.addObjects(...)` writes this grid from placed definitions with `clipped == true`:

- clipped wall cases write value `50` to orientation-specific neighboring grid locations;
- clipped game objects write a model-derived shadow amount, defaulting to `15` and using model height divided by four when a concrete `Model` exists, capped at `30`;
- writes retain the larger existing value.

Therefore exact terrain colors depend on the relevant initial loc placement/shadow side effects being available before terrain construction.

### Underlay neighborhood blend

The builder keeps rolling column totals for:

- weighted hue;
- saturation;
- lightness;
- hue multiplier;
- contributing underlay count.

It adds entries at `+5` and removes entries at `-5`, then performs the same rolling operation on the second axis. Do not replace this with a differently rounded generic convolution.

### Jitter and 3D terrain determinism

The random hue/lightness walk does **not** alter the four underlay corner HSL values passed to `Scene.addTile` for 3D terrain shading.

For underlay:

- non-jittered blended HSL is used with the four slope/shadow lightness values to produce the four 3D corner colors;
- jittered HSL is separately converted through the palette to the stored tile RGB/minimap-style color.

For non-textured overlays the same distinction applies between face HSL and the separately derived palette RGB values.

Consequently, RustOSRS can reproduce the target 3D terrain corner colors deterministically without pinning the random presentation walk. If palette/minimap RGB is represented, jitter must be modeled explicitly.

Hue adjustment uses wraparound:

```text
(hue + rndHue) & 255
```

Lightness adjustment clamps to `0..255`.

### Overlay behavior

The builder preserves these target branches:

- texture ID present: use texture average RGB path and textured tile material;
- primary RGB `0xFF00FF`: use the target sentinel branch and no texture;
- ordinary primary RGB: derive packed HSL and separately derive jittered palette RGB;
- secondary RGB present: derive the secondary jittered palette RGB override.

### Minimum-plane and bridge side effects

The same builder assigns each tile's `minPlane`:

```text
settings bit 8                            -> 0
else plane > 0 and plane-1 bridge bit 2  -> plane - 1
else                                      -> plane
```

The exact source expression checks `tileSettings[1]` for the bridge bit, matching the target scene convention.

After terrain construction, the builder calls scene normal finalization and applies `setLinkBelow` wherever plane-1 settings carry bridge bit `2`.

### Implementation gate

`TERRAIN-004` may become implementation-complete only when RustOSRS has:

1. a production builder that consumes exact decoded floor definitions, heights, settings, placement-derived shadow state, and texture-average inputs;
2. a pinned executable fixture generated from this exact source revision;
3. exact tests for slope/shadow arithmetic, 11x11 border cases, underlay weighted-hue accumulation, overlay sentinel/texture/secondary branches, min-plane output, and bridge relinking;
4. deterministic proof that the 3D face colors do not depend on random hue/lightness state;
5. a separate explicit contract for any palette/minimap RGB that does depend on jitter.

### Prohibited shortcuts

- do not treat `class470` as unrelated merely because most of the class implements text layout;
- do not invent random inputs for 3D terrain corner colors;
- do not describe `Tiles_underlays2` as neighboring-ground contrast;
- do not run terrain color construction before required placement shadow inputs exist;
- do not claim `TERRAIN-004` is implemented until the production fixture passes.

### Failure signature

Large terrain tint differences, incorrect shadows around clipped objects, region-edge blend seams, wrong overlay sentinel behavior, bridge/visibility mistakes, or non-reproducible presentation RGB.
