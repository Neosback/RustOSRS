## SPEC: TERRAIN-001

**Domain:** `OSRS_SEMANTIC`  
**Status:** `VERIFIED`  
**Executable evidence:** existing shape/rotation golden fixture

### Applies to

Shaped tile topology generated by `SceneTileModel`.

### Required behavior

The semantic terrain model supports exactly the audited shape templates `0..12` for this target snapshot. Shape plus rotation determines:

- which template vertices exist;
- vertex positions at tile corners, edge midpoints, and interior quarter/three-quarter points;
- interpolated height at each generated vertex;
- interpolated underlay/overlay corner color input at each generated vertex;
- face count and face indices;
- whether each face consumes underlay-side or overlay-side colors;
- optional face texture assignment.

Rotation remapping must follow the source tables/operations exactly. The resulting generated integer vertices/faces are semantic truth; GPU tessellation must not substitute a topologically different cut.

### Integer semantics

One tile is `128` local units. Midpoint and quarter positions are integer values derived from that unit. Height/color midpoint interpolation follows Java integer arithmetic/order.

### Invariants

- shape/rotation output is deterministic;
- all faces reference generated vertices valid for that shape;
- underlay/overlay ownership is per face as defined by the template, not guessed from geometry;
- a renderer may repack vertices but must preserve generated topology.

### Failure signature

Cracked paths, inverted shoreline wedges, overlay triangles on the wrong half of a tile, rotation-specific seams.

### Required tests

Retain exact golden output for all `13 x 4` shape/rotation combinations. Rust output must match vertex arrays, face indices, color-source selection, texture ids, and flatness exactly.

### Related specs

`TERRAIN-002`, `COORD-001`.

## SPEC: TERRAIN-002

**Domain:** `OSRS_SEMANTIC` for terrain surface meaning; imported RuneLite upload is independent structural corroboration  
**Status:** `VERIFIED` for flat-vs-shaped surface contracts

### Required behavior

A tile terrain surface is represented by either a flat paint surface or a shaped model surface according to the constructed scene state.

For a flat paint surface, semantic inputs are the four corner heights, four corner HSL/color values, optional texture id, and flatness state. The reference upload consumes a consistent two-triangle diagonal split:

```text
NE, NW, SE
SW, SE, NW
```

The `12345678` color sentinel indicates a skipped/unrendered terrain surface in the audited reference path.

For a shaped surface, use the exact generated vertices/faces from `TERRAIN-001`; do not reconstruct a generic quad and mask it in the shader.

### Scope boundary

Packed UV layout, batching, and vertex-buffer representation are renderer policy and belong to Checkpoint 5. The semantic requirement is stable corner/shape ownership and sentinel preservation.

### Failure signature

Opposite tile diagonals, terrain seam changes when switching render backends, hidden/sentinel terrain becoming visible.

### Required tests

Flat tile with four distinct corner heights/colors proving diagonal order, sentinel tile, and shaped-vs-flat representation selection.

### Related specs

`TERRAIN-001`, `FACE-001`.

## SPEC: TERRAIN-003

**Domain:** `OSRS_SEMANTIC`  
**Status:** `VERIFIED` for the pinned floor-definition decode/post-decode behavior

### Underlay definition contract

For the pinned target:

- opcode `1` supplies underlay RGB;
- post-decode converts RGB to HSL-derived fields;
- saturation and lightness clamp to `0..255`;
- `hueMultiplier` is derived from saturation/lightness and clamps to at least `1`;
- stored hue is scaled by the multiplier rather than being an independent raw 0..255 hue.

The weighted-hue representation must be preserved because later terrain neighborhood construction may consume both hue and hueMultiplier separately.

### Overlay definition contract

Defaults:

```text
primaryRgb   = 0
texture      = -1
hideUnderlay = true
secondaryRgb = -1
```

Relevant opcodes:

```text
1 -> primary RGB
2 -> texture id
5 -> hideUnderlay = false
7 -> secondary RGB
```

Post-decode computes secondary HSL fields when secondary RGB exists and then computes/restores the primary HSL fields.

### Invariants

Decode preserves source fields even when the full terrain-color builder is revision-gated. `osrs-cache` must not collapse underlay weighted hue into a single generic HSL value.

### Failure signature

Terrain definitions decode successfully but later blending cannot reproduce reference colors, overlays incorrectly hide/show underlay, secondary color lost.

### Required tests

Known RGB cases at lightness/saturation boundaries, hueMultiplier minimum clamp, overlay defaults and opcodes, secondary+primary post-decode ordering.

### Related specs

`TERRAIN-004`.

## SPEC: TERRAIN-004

**Domain:** `OSRS_SEMANTIC`  
**Status:** `REVISION_SENSITIVE`  
**Implementation dependency:** **BLOCKED unless guarded by an explicitly selected source/profile**

### Subject

Complete terrain color/light construction above decoded floor definitions, including the research claims around slope shading, radius-5/separable 11x11 underlay neighborhood blending, hue weighting, random hue/lightness walk, overlay sentinel/special-color handling, texture average-color fallback, secondary overlay color, and related derived tile flags.

### Evidence state

The pre-blueprint research attributes the complete builder to obfuscated `class470`, but `class470` in the pinned public January 28 commit is unrelated. Therefore those old class/line citations are invalid for this target pin.

Some component helpers and data structures are independently verified, but the complete composition/order is not sufficiently source-pinned to make it unconditional normative behavior.

### Required closure

Promote this spec to `VERIFIED` only after one of:

1. identify and pin the actual terrain builder in the intended deob revision;
2. prove semantic equivalence of that builder to another exact source snapshot; or
3. add an executable end-to-end terrain-color fixture that proves the complete algorithm and inputs.

### Safe requirements before closure

- preserve all decoded fields from `TERRAIN-003`;
- preserve exact HSL helper functions already independently verified in the audit;
- model any random/jitter input explicitly rather than mutating canonical terrain data;
- golden tests must use deterministic jitter inputs;
- never promote the old 11x11 prose merely because it appears plausible.

### Failure signature

Large-scale terrain tint differences, visible region-border color seams, non-reproducible golden screenshots, overlay colors that vary from OSRS despite correct shape geometry.

### Required tests after closure

Neighborhood edge/border cases, hue weighting vs count distinction, no-underlay cells, slope-light grid, overlay magenta/sentinel cases, texture fallback, secondary overlay, fixed jitter and nonzero jitter profiles.

### Related specs

`TERRAIN-003`, `COORD-001`.
